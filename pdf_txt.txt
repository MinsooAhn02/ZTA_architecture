1. Project Overview: Scope and Significance 
Traditional perimeter-based security models (Castle-and-Moat) are no longer sufficient due 
to the rise of cloud computing. This project moves beyond theoretical study to design, 
implement, and validate a functional Zero Trust Architecture (ZTA) platform. 
1.1 Final Deliverable: The "Zero Trust Sandbox" 
The ultimate output of this project is a self-contained Kubernetes-based security testbed. 
This is not just a software installation, but a fully configured environment containing: 
1.  Victim Application: A microservices-based web application designed to simulate a 
real-world target. 
2.  Defense Layer (The ZTA Platform): An integrated control plane (using Istio & OPA) that 
enforces security policies. 
3.  Attack Simulations: A set of scripts that attempt to breach the system, serving as proof 
of the platform's effectiveness. 
1.2 Key Functions: What does it actually do? 
Unlike a standard firewall that sits at the network edge, this platform functions as a 
ubiquitous internal guard: 
●  Traffic Interception: It intercepts 100% of the traffic between internal services 
(East-West traffic), which is invisible to traditional firewalls. 
●  Dynamic Evaluation: It checks Identity (Who?), Context (Where/When?), and Device 
Posture (Is the device healthy/patched?) for every single request. 
●  Micro-segmentation: It isolates a compromised service immediately, preventing the 
attacker from jumping to other servers. 
1.3 Relevance to ZTA: Why build this? 
Zero Trust is often discussed as an abstract concept ("Never Trust, Always Verify"). This 
project translates that abstract concept into concrete engineering: 
●  Implementation of NIST Standards: It directly maps the logical components of NIST SP 
800-207 (Policy Decision Point, Policy Enforcement Point) to actual software (OPA, Istio). 
●  Proof of Concept: It demonstrates how to remove implicit trust from a network, showing 
that ZTA is a viable engineering solution, not just a policy. 
1.4 Project Benefits: What will be gained? 
By building this platform, the project aims to achieve: 
1.  Verification of Theory: Empirically proving that ZTA can stop lateral movement where 
traditional models fail. 
2.  Practical Engineering Skills: Gaining hands-on expertise with industry-standard 
Cloud-Native tools (Kubernetes, Service Mesh). 
3.  Bridging the Gap: Understanding the complexity of implementing security policies in a 
live, distributed system. 
2. Problem Statement & Scenarios 
This project focuses on mitigating the following specific security scenarios by implementing 
the ZTA prototype: 
Scenario A: Prevention of Lateral Movement 
●  Problem: An attacker compromises a frontend web server. In a flat network, they can 
immediately scan and access the backend database. 
●  Goal: The prototype should deny access to the database unless specific, dynamic 
criteria are met, verifying that the implementation successfully segments the network. 
Scenario B: Context & Device Posture Access Control 
●  Problem: A valid user's credentials are stolen, or a legitimate user attempts access from 
a compromised/outdated device (e.g., OS vulnerabilities, disabled firewall). 
●  Goal: The platform should detect device health status and context changes (location, 
time), enforcing policy blocks if the device is deemed insecure, even with valid 
credentials. 
3. Implementation Approach & Tools 
To solve the problems above, the platform will be constructed using a Service Mesh and 
Policy as Code approach. 
Note: The following software components are selected as tools to implement and 
evaluate the proposed ZTA platform. These are not contributions in themselves but 
serve as practical means to produce the prototype and observe system behavior. 
3.1 Architecture Overview 
1.  Policy Decision Point (PDP): The "brain" (OPA) that evaluates requests against policies. 
2.  Policy Enforcement Point (PEP): The "gatekeeper" (Istio/Envoy) that intercepts traffic. 
3.  Identity Provider (IdP): The authentication authority (Keycloak). 
3.2 Technology Stack 
●  Infrastructure: Kubernetes (K8s) or Minikube. 
●  Service Mesh: Istio (uses Envoy Proxy) for traffic interception and mTLS. 
●  Policy Engine: OPA (Open Policy Agent) for defining access rules in Rego. 
●  Identity Management: Keycloak for OIDC/JWT management. 
●  VPN/Tunneling (Baseline): WireGuard and OpenVPN may be used to establish secure 
remote access baselines for comparison.
